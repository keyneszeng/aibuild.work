# Lesson 1 — AI Product Basics

## I. Learning Goals

- **Knowledge**: Build a holistic "AI product" cognitive map — it covers the full chain from discovering a problem to launching and measuring; understand that an AI product is not a pile of features but a combination of "capability × scenario × boundary"; know the PM's role in AI projects.
- **Ability**: Draw your own "AI product capability map," marking which capabilities you can do yourself and which need technical support.
- **Artifact**: An *AI Product Capability Map* (structured with reference to deanpeters/Product-Manager-Skills' 70 Skills framework).

> This lesson's framework references deanpeters/Product-Manager-Skills (an AI-agents-oriented PM skill system, including Foundation + the five Triple Diamond stages) and product-on-purpose/pm-skills.

## II. Warm-up Question

> Everyone's talking about "building AI products" — as a PM, what exactly do you need to know?
> Same "add some AI," so why is one product stunning while another feels like a toy?
> When you discuss requirements with your technical colleagues, how do you make them understand what you want?

The hard part of AI products isn't "connecting a model" — it's "thinking clearly about where to use it, how to use it, and where the boundary is." This lesson gives you a map.

## III. Core Concepts

### 1. The Full Chain of an AI Product
Following the deanpeters framework, the PM's work runs through: Foundation (persona/canvas/OKR and other general capabilities) → Discover (find the right problem) → Define (frame the problem) → Develop (explore solutions) → Deliver (launch) → Measure (validate with data) → Iterate. You are present at every link.

### 2. The Meaning of a Capability Map
Drawing "what I need to learn" as a diagram shows where the gaps are and what to fill. Common capability domains: user research, problem definition, solution design, PRD, evaluation, risk & compliance, commercialization.

### 3. Where PM Differs from Traditional Software PM
A traditional PM defines deterministic logic; an AI PM must also manage "uncertainty" — the model can err, drift, and needs evaluation. This is the main thread of the lessons to come.

### 4. Red Line: Don't Show Off Techniques
AI is a means; user value is the end. Your capability map must always reserve a slot for "user value."

## IV. Worked Example (Real Product Scenario)

### Case: Launching an AI Feature with Foundation Skills
- persona: first generate an evidence-backed user persona (with confidence level)
- lean-canvas: write the problem / customer / value proposition / metrics on one page
- okr-writer: turn goals into measurable key results
**Value**: start the project with structured tools instead of guessing.

## V. Hands-on Task

- **Background**: You are about to own an AI feature.
- **Input**: a rough idea.
- **Steps**:
  1. Use the "capability map template" to list 7 capability domains and self-rate your proficiency.
  2. Mark the 3 most critical domains for this project.
  3. Produce one page each with persona + lean-canvas.
- **Expected output**: *AI Product Capability Map* + one page each of persona/lean-canvas.

## VI. Prompt / Design Template

```
You are now playing: AI Product Mentor
I want to sort out my capability map. The capability domains are: [user research / problem definition / solution design / PRD / evaluation / risk & compliance / commercialization]
Please help me: ① generate a self-assessment table (1–5 score per domain + gap notes) ② for the [feature] I'm about to build, point out the 3 most critical domains.
```

## VII. Human Review Checklist

- [ ] Capability map covers the full chain, not just features
- [ ] The user-value slot is filled in and specific
- [ ] persona/lean-canvas has a real basis

## VIII. Common Mistakes

1. Only listing features, not drawing a capability map.
2. Missing the "evaluation / risk" blocks from the map.
3. Treating AI as an end rather than a means.
