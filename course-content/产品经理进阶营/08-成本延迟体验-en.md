# Lesson 8 — Cost / Latency / Experience

## I. Learning Goals

- **Knowledge**: Understand the engineering-constraint triangle of AI products — the trade-off between token cost, response latency, throughput, and experience; know that the PM must make decisions between "quality" and "cost / speed."
- **Ability**: Draw an "engineering-constraint table" for a feature, listing cost sources, latency expectations, and experience trade-offs.
- **Artifact**: An *Engineering Constraint Table* (for technical review).

> This lesson references Deanpeters' Deliver/Measure stages, mlabonne/llm-course's deployment and cost considerations, and Generative-AI-For-Beginners' production chapter.

## II. Warm-up Question

> A top-tier LLM is stunning, but each call costs tens of cents and the user waits 10 seconds — can you sustain that?
> Why do some products get by with a cheap small model?
> Can "fast" and "accurate" both be had?

The PM of an AI product must know how to do the math. Quality isn't the only metric — cost and speed decide whether you survive.

## III. Core Concepts

### 1. Cost Comes from Tokens
Input + output are both billed. Long context, multi-turn, and RAG-retrieved passages all inflate cost. The PM must control "how much to feed."

### 2. Latency
The bigger the model, the slower; streaming output eases the "waiting" feeling. The PM must set "the response time users will accept."

### 3. Experience Trade-off
- Critical scenarios (first customer-service response): prioritize speed, use small model / cache.
- Complex scenarios (writing a plan): slow is acceptable, use a large model.
- Hybrid: route simple cases to a small model, escalate hard ones to a large model.

### 4. Cache & Reuse
Cache answers to frequently identical questions to cut cost and speed things up.

## IV. Worked Example (Real Product Scenario)

### Case: Cost Control for an AI Writing Assistant
- Problem: every call carries the full materials, token explosion.
- Solution: first retrieve relevant passages (fewer tokens) + cache common templates.
- Result: cost down 60%, first response twice as fast.
**Value**: the PM's constraint design directly saves money.

## V. Hands-on Task

- **Background**: Assess constraints for a feature.
- **Input**: feature and expected usage.
- **Steps**:
  1. List cost sources (context / multi-turn / retrieval).
  2. Set latency expectation and experience priority.
  3. Write the trade-off decision (when to use small / large model).
- **Expected output**: *Engineering Constraint Table*.

## VI. Prompt / Design Template

```
Feature: [ ] Expected daily calls: [ ]
Please output an engineering-constraint table: ① cost sources and estimation basis ② user-acceptable latency ③ experience priority (fast / accurate / complete) ④ small/large model routing strategy ⑤ cost-reduction means (cache / chunking / retrieval).
```

## VII. Human Review Checklist

- [ ] Cost sources identified and estimable
- [ ] Latency expectation has a user basis
- [ ] Has model routing / cost-reduction strategy
- [ ] Experience trade-off is explicit

## VIII. Common Mistakes

1. Only chase quality, ignore cost — can't run.
2. No latency expectation — user churn.
3. One-size-fits-all large model regardless of scenario.

## IX. Homework (Deliverables)

Submit one *Engineering Constraint Table*.

## X. Grading Rubric

- Completion: table complete (40%)
- Quality: cost / latency / routing reasonable (35%)
- Decision: trade-off is evidence-based (25%)
